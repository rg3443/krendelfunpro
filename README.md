# Telegram-бот аренды ботов для Twitch-чатов (C++)

Бот принимает оплату по СБП на внутренний баланс, оформляет заказы (канал, количество ботов, время),
списывает стоимость с баланса и уведомляет пользователя о каждом изменении статуса заказа.

## Возможности

**Пользователь**
- `💰 Баланс` / `➕ Пополнить` — счёт на оплату через **СБП** (ЮKassa). Зачисление автоматическое:
  фоновый поток опрашивает статус платежа, плюс кнопка «Проверить оплату».
- `🛒 Заказать ботов` — 4 шага: канал (логин или ссылка twitch.tv) → **тип ботов** → число ботов → часы → подтверждение.
  Цена = `боты × часы × цена тарифа`. Если денег не хватает — черновик сохраняется, можно пополнить и подтвердить.
- **Тарифы** (`pricing.tiers`, цена за 1 бота в час): 🧠 умный бот (Claude Opus) — 100 ₽, 🤖 простой — 10 ₽.
  Подробное описание тарифа показывается по кнопке «ℹ️ Подробнее» (на шаге выбора тарифа, в приветствии и
  по `/tariffs`). Текст для `smart`/`dumb` встроен в код (`defaultTierDetails` в [src/config.cpp](src/config.cpp)),
  его можно заменить полем `details` тарифа (строка или массив строк, HTML Telegram). Описание соответствует
  поведению ботов на сервере (`prompts/tier_*.txt`; умные — на общей модели сервера, сейчас `opus`):
  если на сервере сменить модель или поведение, поправьте и текст.
- На шаге выбора количества бот спрашивает у сервера `/api/status` и пишет, сколько ботов свободно
  (и сколько всего). Заказать можно больше — сервер стартует со свободными и добирает остальных.
  Тариф и цена бот-часа запоминаются в заказе: продление идёт по той же цене, даже если тарифы поменяли.
  Если тариф один — шаг выбора пропускается.
- `📦 Мои заказы` — последние 10 заказов со статусами.
  **Отмена** (`🚫 Отменить` в «Мои заказы» / в сообщении о запуске, или `/cancel` → список активных заказов →
  подтверждение): боты сразу уходят из чата (бот вызывает `/stop` у сервера). `/cancel` во время диалога
  (оформление заказа, ввод суммы) прерывает только диалог.
  **Деньги при отмене заказчиком не возвращаются** (`refund_on_cancel: false`); при `true` — возвращается
  неиспользованное время (заказ в очереди — вся сумма). Возвраты по вине сервиса (заказ не запустился,
  канал не найден, заказ снят на сервере, недоданные боты) работают всегда.
  Идущий заказ можно **продлить** (`⏩ Продлить` → +N часов → подтверждение). За `remind_before_min` минут до конца
  бот сам присылает напоминание с кнопкой продления.
- Уведомления: заказ принят → запущен (с временем окончания) → завершён; отклонён/прерван (с суммой возврата);
  платёж зачислен / отменён / истёк.

**Администратор** (`admin_ids` в конфиге), `/admin` — список команд:
- уведомление о новом заказе с кнопками «▶️ Запустить» / «❌ Отклонить» (в ручном режиме);
- `/stats`, `/queue`, `/user <tg_id>`;
- `/startorder <id>`, `/failorder <id> [причина]` — прервать заказ с возвратом неиспользованного времени;
- `/addbalance <tg_id> <сумма>` (с минусом — списание), `/paid <payment_id>` — ручное подтверждение платежа.

## Статусы

| Заказ | Значение |
|---|---|
| `queued` | оплачен, ждёт запуска (можно отменить с полным возвратом) |
| `running` | боты в чате до `ends_at` |
| `completed` | время вышло |
| `cancelled` | отменён пользователем |
| `failed` | отклонён/прерван, остаток возвращён пропорционально времени |

Платёж: `new → pending → succeeded | canceled | expired | error`.
Все деньги хранятся в копейках (`int64`); списание, зачисление и возврат — атомарные транзакции SQLite,
каждая операция пишется в таблицу `transactions`. Повторное зачисление одного платежа невозможно.

## Исполнитель заказов

Сам запуск ботов в Twitch-чате вынесен за интерфейс `OrderExecutor` ([src/executor.hpp](src/executor.hpp)):

- `manual` — админ получает заказ и после запуска жмёт «Запустить»; по окончании времени бот
  завершает заказ, уведомляет клиента и напоминает админу отключить ботов.
- `http` — бот сам работает с сервером ботов (совместим с `krendelbot`), заголовок `Authorization: Bearer {token}`:
  - перед запуском `GET {url}/status` → `bots_free`; если свободных ботов 0, заказ ждёт в очереди, время не тратится;
  - `POST {url}/start` `{"order_id", "channel", "bots", "hours", "ends_at"}` → состояние заказа
    (`status`, `bots_assigned`, `ends_at`). Клиенту честно пишется, сколько ботов реально зашло;
  - каждые `poll_interval_sec` — `GET {url}/orders/{order_id}`:
    - `running` / `waiting`: за недостающих ботов копятся «недоданные бот-секунды». При завершении
      клиенту возвращается `цена × недоданные / (боты × длительность)`;
    - `paused` (kill switch в чате) — клиенту уведомление, это время не компенсируется;
    - `failed` (например, канал не найден) или досрочный `stopped` — заказ закрывается, клиенту возвращается
      остаток времени и компенсация, админам приходит уведомление;
    - `404` (заказ удалён на сервере через `DELETE /api/orders/{id}`) — заказ закрывается с возвратом остатка;
  - `POST {url}/orders/{order_id}/extend` `{"hours"}` — продление. Сначала деньги списываются и срок сдвигается
    в базе бота (одной транзакцией), затем запрос на сервер; если сервер отказал (например, 409 — заказ уже
    завершился), продление откатывается и деньги возвращаются. В последнюю минуту заказа продлить нельзя;
  - `POST {url}/stop` `{"order_id", "reason"}` по окончании или при прерывании.

  Номер заказа на сервере = `order_id_offset` (по умолчанию 100000) + номер в боте, чтобы не пересекаться
  с заказами, созданными из консоли сервера. Если за `auto_start_timeout_min` запустить не удалось
  (нет свободных ботов или сервер недоступен) — отказ с полным возвратом.

## Оплата по СБП (ЮKassa)

1. Подключите магазин в ЮKassa и способ оплаты «СБП».
2. В конфиге: `"provider": "yookassa"`, `shop_id`, `secret_key`, `return_url` (ссылка на бота).
3. **Выбор способа оплаты** (`payments.payment_methods`, по умолчанию `["sbp", "bank_card"]`): после выбора
   суммы бот спрашивает «⚡ СБП / 💳 Банковская карта». Один способ в списке — без вопроса, `[]` — способ
   выбирается на странице ЮKassa. Если выбранный способ не подключён в магазине (ЮKassa отвечает
   `Payment method is not available`, например СБП в тестовом магазине), бот предлагает оставшиеся способы.
   Платёж создаётся с `payment_method_data.type` = выбранный способ,
   `capture: true`, Idempotence-Key — случайный UUID на каждый счёт (ключ из одного номера платежа конфликтовал бы между копиями
   бота с разными БД на одном магазине: ЮKassa помнит ключи 24 ч). Пользователь получает кнопку-ссылку на оплату.
   Если ЮKassa отклонила запрос, в лог пишется её `code`, `description` и `parameter`.

**Чеки 54-ФЗ** (`payments.receipt.enabled: true`): в каждый платёж добавляется `receipt` — покупатель
(email или телефон), одна позиция на сумму платежа, `vat_code`, `payment_subject`, `payment_mode`,
при необходимости `tax_system_code`. Перед первой оплатой бот спрашивает у клиента email или телефон
(можно кнопкой «📱 Отправить мой телефон»), сохраняет его и дальше не спрашивает; изменить — `/contact`
или кнопка в «Баланс». По умолчанию пополнение баланса пробивается как аванс (`advance` + `payment`) —
значения согласуйте с бухгалтером.

**Тестирование:**
- `"provider": "mock"` — счёт создаётся, админ подтверждает его `/paid <id>`, без ЮKassa;
- тестовый магазин ЮKassa (ключ `test_...`) — `"provider": "yookassa"`; если в тестовом магазине нет СБП,
  бот при выборе СБП сам предложит карту — платите тестовыми картами ЮKassa; чеки в тестовом магазине
  тоже можно включить, чтобы проверить, что ЮKassa принимает `receipt`;
- `build\payments_test.exe` — проверка тела запроса (способ оплаты, чек) без сети;
- `build\payments_live_test.exe config.json` — создаёт по платежу СБП и картой в **тестовом** магазине
  (с ключом `live_` не запускается) и показывает, какие способы реально доступны.
Чтобы подключить другой банк (Т-Банк, Точка и т.п.), реализуйте `PaymentProvider` в [src/payments.hpp](src/payments.hpp).

## Сборка (Windows, MSVC + vcpkg)

Зависимости: cpr, nlohmann-json, sqlite3 (на Windows — `vcpkg.json`, на Linux — пакеты apt).

```bash
build.bat
```

`build.bat clean` — сборка с нуля. Скрипт собирает тем же MSVC (VS 18 Build Tools), которым vcpkg собрал
зависимости: если собрать генератором «Visual Studio 17 2022», линковка cpr упадёт с
`__std_find_first_of_trivial_pos_1`.

С русскоязычным MSVC генератор NMake не отслеживает изменения заголовков, и после их правки оставались
устаревшие `.obj` — программа падала при запуске с кодом `0xC0000409`. Поэтому в `CMakeLists.txt` каждый
`.cpp` явно зависит от всех заголовков `src/*.hpp`.

Тесты:
- `build\db_test.exe` — баланс, платежи, заказы, возвраты и компенсация за недоданных ботов;
- `build\payments_test.exe` — запрос к ЮKassa (способ оплаты, чек 54-ФЗ), разбор email/телефона;
- `build\exec_test.exe` — обмен с сервером ботов; перед запуском поднимите фейковый сервер:
  `python tests\fake_krendelbot.py 18080 secret`.

## Linux-сервер (Ubuntu 24.04 / Debian 12)

Код один и тот же, переписывать ничего не нужно. На Linux зависимости берутся из apt (vcpkg не нужен):
`nlohmann-json3-dev`, `libsqlite3-dev`, `libcurl4-openssl-dev`. Пакета cpr в Ubuntu 24.04 и Debian 12 нет — CMake сам
скачает cpr 1.10.5 и соберёт поверх системного libcurl (нужен доступ к github.com при первой сборке).

```bash
bash build.sh deps     # один раз: поставить пакеты (sudo) и собрать
bash build.sh          # пересборка
bash build.sh test     # сборка + db_test, payments_test, exec_test (фейковый сервер поднимается сам)
```

**Установка как службы** (автозапуск, перезапуск при падении, логи в journald):

```bash
sudo useradd --system --home /opt/rentbot --shell /usr/sbin/nologin rentbot
sudo mkdir -p /opt/rentbot && sudo chown $USER /opt/rentbot
# скопировать проект в /opt/rentbot (git clone / scp / rsync), затем:
cd /opt/rentbot && bash build.sh deps
# config.json и rentbot.db можно перенести с Windows как есть (бота на Windows перед этим остановить)
sudo chown -R rentbot:rentbot /opt/rentbot && sudo chmod 600 /opt/rentbot/config.json
sudo cp deploy/rentbot.service /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl enable --now rentbot
journalctl -u rentbot -f        # логи
sudo systemctl restart rentbot  # после пересборки или правки config.json
```

- Время в сообщениях клиентам берётся из часового пояса процесса: в юните стоит `TZ=Europe/Moscow`
  (VPS обычно в UTC).
- Одновременно должен работать только один экземпляр бота с этим токеном — иначе Telegram отдаёт ошибку
  `409 Conflict` на long polling.
- Сервер ботов на той же машине — `executor.url` остаётся `http://127.0.0.1:8080/api`; порт 8080 наружу
  не открывайте. Если сервер на другой машине — укажите его адрес и ограничьте доступ файрволом.
- Бэкап — файл `rentbot.db` (в режиме WAL копируйте вместе с `-wal`/`-shm` при остановленном боте или
  `sqlite3 rentbot.db ".backup backup.db"` на ходу).

## Запуск

```bash
copy config.example.json config.json
```

Заполните `config.json` (токен, admin_ids, платёжные данные) и запустите:

```bash
build\rentbot.exe config.json
```

DLL зависимостей vcpkg копирует рядом с exe автоматически. Остановка — Ctrl+C.

## Структура

```
src/main.cpp       точка входа
src/bot.*          меню, диалоги, заказы, уведомления, админка, фоновый поток
src/db.*           SQLite: пользователи, баланс, платежи, заказы, журнал операций
src/payments.*     ЮKassa (СБП) и mock-провайдер
src/executor.*     ручной и HTTP-исполнитель заказов
src/telegram.*     минимальный клиент Bot API (long polling)
src/config.*       загрузка config.json
build.bat / build.sh  сборка на Windows / Linux
deploy/rentbot.service  systemd-юнит
```
